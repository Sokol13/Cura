## Performance and media evidence

The final [Node 22](evidence/v0.4.0/node22-stress-05-attempt-0.json) and [Node 24](evidence/v0.4.0/node24-stress-05-attempt-0.json) runs registered 1,000 generated images through the real server, decoded every thumbnail and observed the new watched file in the UI. Each measured 70 API queries across 14 search/filter combinations and five browser input-to-paint samples.

| ------------------------------------- | ------------------ | ------------------ | ------------------------------ |
| Initial 1,000-image ingestion         | 11.151 s           | 10.118 s           | Complete scan without crash    |
| Thumbnails requested / decoded        | 1,000 / 1,000      | 1,000 / 1,000      | All decoded; no failures       |
| Slowest sampled API query             | 54.26 ms           | 58.80 ms           | <200 ms                        |

| List frame p95 / maximum              | 16.8 / 33.3 ms     | 16.8 / 33.3 ms     | Existing frame gates unchanged |

These are measured Linux headless-browser samples, not a guarantee for every query or physical display. Grid/list traces reported no Long Tasks; virtualized rendering retained bounded visible rows. Real SD and ComfyUI imports automatically exposed the Chinese prompt phrase and model, including exact seed handling. The offline scenarios block and record non-loopback browser HTTP/WebSocket traffic; this is browser-level isolation, not an operating-system packet-capture claim.

Canvas performance was measured in four production-build scenarios per runtime: a populated 100-node canvas, slot-history comparison, a filled 10×10 matrix, and the canvas at controlled DPR 1.25. Every scenario observed 15 seconds of idle activity and ten complete sequential CDP screenshots. Across the final eight scenarios, idle frame p95 was 16.7–16.8 ms, idle maximum was 16.8 ms, and all 80 captures finished within the unchanged 3-second deadline. The slowest capture was 209.36 ms on Node 22 and 201.10 ms on Node 24. Capture-load frame maximum reached 50.1 ms; it is not reported as the idle maximum. No Long Tasks, observed DOM mutations, resize callbacks, layout/style-recalculation increments or unexpected board revisions occurred during the measured windows. The matrix has 100 decoded images, of which 15 intersected the viewport; it is not presented as 100 simultaneously visible images.

[The focused investigation](evidence/v0.4.0/canvas-performance/README.md) and final per-runtime canvas JSON files retain DOM, request, renderer and capture measurements. They use Linux software rendering/SwiftShader. No React commit counter was injected, so DOM/CDP observations are not a React-render or GPU-paint count. The reported Windows canvas/CDP freeze was not reproduced; no speculative production optimization or Windows fix is claimed.

[The PSD benchmark](evidence/v0.4.0/runtime-acceptance/runtime-psd-summary.json) used generated files at 3866×6871, 8192×8192 and 13391×7032, each larger than 50 MiB. The first two exercise embedded resource 1036/1033; the third exercises the merged raw composite. Full-server measurements include worker/native memory and retain the original <10-second processing and <500,000,000-byte absolute process-RSS limits.
